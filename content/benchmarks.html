RunMQ vs BullMQ — the numbers.

A fair, reproducible benchmark comparing RunMQ (RabbitMQ) and BullMQ (Redis) across six performance dimensions. Tested on MacBook Pro M4 Max, Docker Desktop, mean of 3 runs ± stddev.

Why this comparison exists. BullMQ is the most popular queue in Node land, so it's the natural reference point — and people kept asking. This page is here mostly out of curiosity. RunMQ isn't trying to win benchmarks. Its goal is durability and reliability for production systems running at scale: broker-driven retries, dead-lettering, backpressure, observability via Pulse, predictable behavior under failure. That said, the numbers below show RunMQ holds its own — and is faster in most cases — which is a nice bonus, but not the reason to pick it.
Transparency. The benchmark was written by Claude (Anthropic) at the request of the RunMQ maintainer, with explicit instructions to optimize BullMQ to the maximum (addBulk(), skipStalledCheck, skipLockRenewal, etc.). Both libraries got equal Docker resources (2 CPU, 4 GB RAM) and identical settling time. The two systems have fundamentally different architectures, so see Known caveats for what these numbers really mean.
What changed in 2.x. RunMQ 2.x turns on publisher confirms by default — every publish() now awaits a broker ack before resolving, so silent drops become loud failures. That guarantee costs throughput: publish drops from 253k → 67k msg/s on the 100 B path. We made the call deliberately — reliability over raw speed — and even after the drop, RunMQ's confirmed publish is still 1.3× faster than BullMQ's confirmed addBulk(). If you need the old fire-and-forget behavior, opt out with usePublisherConfirms: false. Switch the toggle above to compare 1.x and 2.x numbers side by side.

Throughput at a glance

Publish throughput (msg/s)

What this measures: how many messages per second a single producer can push, with no consumer attached. Each library publishes a fixed total (10,000 messages, 100-byte payload) and the elapsed time gives msg/s.

4.7× faster. RunMQ 1.x publishes via in-process AMQP buffer (fire-and-forget); BullMQ awaits a Redis pipeline round-trip.

1.3× faster. Both libraries now await confirmed persistence — RunMQ's publish() waits for a broker ack (publisher confirms on by default in 2.x), BullMQ's addBulk() awaits a Redis pipeline round-trip. The drop from 1.x's 253k msg/s is the price of that broker ack — see the callout above.

Consume throughput (msg/s)

What this measures: how fast a single no-op consumer drains a pre-loaded queue. The queue is filled with 10,000 messages, then a consumer with a no-op handler is started; timing runs from the first message consumed to the last.

3.3× faster. RunMQ pulls comfortably ahead on the consume path. Its push-based delivery keeps each consumer's local prefetch buffer full, so it never round-trips to fetch the next message — where BullMQ's pull model pays a Redis round-trip per job. That difference is what opens the gap as the queue drains.

2.6× faster. The same push-vs-pull advantage holds here: RunMQ stays well ahead because its consumers always have the next message buffered locally, while BullMQ remains bound by per-job Redis round-trips.

Concurrent consumers (msg/s, 1ms simulated work)

What this measures: drain rate when handlers do non-trivial work — each handler awaits a 1 ms sleep before acking. Two configurations: one in-flight message at a time (1) and eight in-flight per process (8). This isolates how well each library overlaps I/O across concurrent in-flight messages.

The gap is widest at low concurrency. With a single message in flight, RunMQ's push-based prefetch keeps the consumer fed while BullMQ pays a full Redis round-trip per job — so RunMQ runs ~17× faster. As concurrency rises to eight, BullMQ overlaps those round-trips and closes some of the distance, but RunMQ stays 6–9× ahead because it never has to stop and fetch the next message.

Known caveats

  • Confirmed publishes by default in 2.x. RunMQ 2.x's publish() awaits a broker ack out of the box (publisher confirms enabled by default), measuring "confirmed persistence speed" — the same guarantee BullMQ's addBulk() provides via its Redis pipeline confirmation. The 2.x headline numbers reflect this confirmed-persistence path. RunMQ 1.x publishes were fire-and-forget into the AMQP buffer, which is why its publish throughput is much higher but came with no delivery guarantee. If you opt out of confirms in 2.x via usePublisherConfirms: false, you recover 1.x-style publish throughput, but the comparison stops being apples-to-apples.
  • Redis is in-memory, RabbitMQ is disk-backed. RabbitMQ persists messages to durable queues by default; Redis operates entirely in-memory. This always favors BullMQ on raw latency.
  • Execution ordering is fixed. RunMQ runs first in every scenario, paying the JIT cold-start cost. This biases against RunMQ.
  • 1 ms simulated work in concurrent-consumer tests over-weights per-message overhead. Realistic 10–100 ms work would narrow the gap.
